# 回归测试说明

## 1. 测试入口

在工程根目录运行：

```bash
python ./test/run_regression.py
```

默认使用 Windows 构建入口：

```text
build.bat
```

可以显式选择构建脚本：

```bash
python ./test/run_regression.py --os windows
python ./test/run_regression.py --os linux
```

`--os windows` 使用 `build.bat`，`--os linux` 使用 `bash ./build.sh`。

## 2. 测试组织

回归测试分为两类：

```text
test/basic/      通用 basic tests，检查编译器不变量
test/modelX/     golden model fixtures，比较 target/all.coe
```

`test/run_regression.py` 会先调用 `test/basic_runner.py` 发现并运行：

```text
test/basic/test_*.py
```

每个 basic test 文件必须暴露：

```python
def run(ctx) -> None:
    ...
```

`ctx` 由 `basic_runner.py` 提供，负责 patch/恢复 `python/npu_config.py`、执行 build/clean、读取构建产物和计算 hash。basic test 不应直接复制 fixture 文件，也不应直接管理全局现场。

basic tests 全部通过后，`test/run_regression.py` 再遍历 `./test` 下除以下目录以外的所有子目录作为 golden fixture：

```text
basic
tools
error
__pycache__
```

每个 fixture 子目录都是一个完整回归用例，例如：

```text
test/model1/
test/model2/
...
```

每个 fixture 目录必须包含统一命名的文件：

```text
model.pt2
npu_config.py
intr_move.json
all.coe
```

可选文件：

```text
all.coe.map.txt
```

`all.coe.map.txt` 不参与自动判定，只在发生错误时辅助人工排查。

## 3. npu_config.py 路径约定

fixture 自己的 `npu_config.py` 应使用从工程根目录出发的相对路径，例如：

```python
MODEL_PATH = "./test/model1/model.pt2"
INTR_MOVE_PATH = "./test/model1/intr_move.json"
```

回归脚本只会把 fixture 目录中的 `npu_config.py` 复制到：

```text
python/npu_config.py
```

不会复制 `model.pt2` 或 `intr_move.json`。这能保证模型和截位配置始终由 fixture 自己持有，避免污染工程根目录。

## 4. 执行流程

整体执行顺序：

```text
1. 备份原始 python/npu_config.py。
2. 运行 test/basic/test_*.py。
3. 若任一 basic test 失败：写入 test/error/，停止，不再运行 model fixtures。
4. basic 全部通过后，运行 test/modelX golden fixtures。
5. 若任一 model fixture 失败：写入 test/error/，停止。
6. finally 中恢复原始 python/npu_config.py，并执行 build clean。
```

当前 basic tests 包括：

```text
test_parse_limit_equivalence.py  : MODE=1 与 MODE=2 + 有效 op 上限产物一致
test_limit_overflow.py           : LIMIT 超过有效 op 数时与 MODE=1 产物一致
test_runtime_limit.py           : RUNTIME_LIMIT_ADDR 过小时构建失败并报告 runtime 越界
test_rebuild_determinism.py      : 相同配置连续构建 all.coe hash 一致
test_clean_contract.py           : build 生成关键产物，clean 删除关键产物
test_memory_plan_integrity.py    : memory_plan region 不重叠，instr/map 大小一致
test_npu_bin_export.py         : 构建后按 memory_plan 自动校验 npu_params.bin / npu_instr.bin 与 COE 内容一致
test_passthrough_not_in_ir.py    : flatten/clamp/to/floor 等透传节点不写入 IR
```

对每个 `test/modelX` fixture，脚本执行：

```text
1. 检查 model.pt2 / npu_config.py / intr_move.json / all.coe 是否存在。
2. 执行 build clean。
3. 将 fixture 的 npu_config.py 复制到 python/npu_config.py。
4. 执行 build。
5. 调用 test/tools/diff.py 比较 test/modelX/all.coe 和 target/all.coe。
6. 记录通过或失败。
```

无论测试结果如何，脚本最后都会：

```text
1. 恢复原 python/npu_config.py。
2. 执行 build clean。
```

## 5. 判定规则

basic test 通过条件由对应 `test/basic/test_*.py` 的断言决定。basic test 只检查通用编译器不变量，不应写死当前模型的通道数、算子个数、地址或 FULL 数量。

model fixture 通过条件：

```text
target/all.coe 与 test/modelX/all.coe 完全一致
```

如果 basic test 断言失败、build 失败、必需文件缺失或 COE 不一致，则当前测试失败；脚本会停止后续测试。

## 6. 错误日志

失败日志写入：

```text
test/error/
```

若需要清理这些错误日志，可以在工程根目录运行：

```bash
./build.sh distclean
```

或在 Windows cmd 中运行：

```bat
.\build.bat distclean
```

日志名包含失败用例名和时间戳，例如：

```text
test/error/model1_20260708_203012.log.txt
test/error/basic_test_limit_overflow_20260712_203012.log.txt
```

basic test 失败时，日志会包含异常信息和本次执行过的 build/clean 命令输出。

model fixture 的 COE 不一致时，日志会包含：

```text
首个不同行号
该行 expected / actual 内容
test/tools/diff.py 的输出
fixture all.coe.map.txt 和 target/all.coe.map.txt 的路径提示
```

这样可以先用日志定位差异，再结合 map 文件人工检查内存布局。

## 7. 成功输出

全部用例通过时，脚本最后输出类似：

```text
[SUMMARY] basic_passed=6 basic_failed=0 model_passed=1 model_failed=0
```
